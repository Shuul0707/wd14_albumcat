# 图片类型分类：插画 / 梗图 / 照片 / 截图

给相册里的人一个「这张是插画还是别的什么」的答案。它不是又一个独立模型——输入是 WD14
（`wd-v1-4-vit-tagger-v2`）在 448×448 上抽出的 **768 维特征**，再拼上 Chinese-CLIP 的
**512 维**（就是语义搜索用的那个塔），一共 1,280 维，接一个 4 类的 softmax，20 KB，
头本身跑一张图不到 1 ms，跟着 WD14 一起在 `/plan` 里返回。

| 类别 | 标签 | 典型内容 |
| --- | --- | --- |
| `illustration` | `插画` | 二次元插画、AI 画、漫画分镜、动画截图 |
| `meme` | `梗图` | 带字幕/描边字的梗图、表情包、Twitter 式截图 |
| `photo` | `照片` | 相机拍的真实照片（含 cosplay、手办、油画照片这类难例） |
| `screenshot` | `截图` | 手机/网页 UI 截图、文档截图 |

四类**互斥**：一张图只会拿到一个标签。冠军置信度低于 `threshold`（默认 0.5）时**一个标签都不发**——
宁可留空，也不把真实照片塞进「插画」。

## 两类人怎么用它

| 想干的事 | 用哪个入口 |
| --- | --- |
| 找某个角色的插画、梗图、表情包 | `角色\|…` 里的角色名，或者直接搜「黑暗的初音未来」 |
| 只整理收藏的插画，不想混进梗图 / 表情包 / 截图 | Tags 页点 `插画` |
| 反过来，只想看梗图/表情包 | Tags 页点 `梗图` |

两套标签是叠加的，不是二选一：一张初音未来的插画同时有 `角色|初音未来` 和 `插画`，
按角色筛、按类型筛、把两者一起搜都行。

⚠️ 手机端「只标角色（推荐）」勾着的时候，客户端只保存角色标签，`插画` 这类普通标签会被丢掉。
想拿到类型标签，把那个勾去掉（`设置 → AI 打标签 → 只标角色`），或只对插画目录单独跑一轮。

## 版本演进：v2 换数据、v5 接 CLIP

第一版（2026-07，2,222 张）的「梗图」类用的是 HuggingFace `neuralcatcher/hateful_memes`——
**欧美照片模板 + 白底黑字**，一张二次元梗图都没有。于是「动漫插画裁掉一块 + 一行描边字」
在训练数据里根本不存在，模型只能把它当插画，`exclusive` 又只发冠军，用户看到的就是
「二次元梗图基本都被分类为插画」。域内 99.8% 全对是真的，域外这个场景 100% 错也是真的。

v2 换了数据（正样本 = safebooru 的 `meme` 标签，难负样本 = 带字的普通插画），把动漫梗图从
「几乎 100% 漏进插画」压到 8%。v5 再把 CLIP 向量拼进来、把照片和截图两类各扩到两千张上下，
`插画` 的召回从 v2 的 0.75 提到 0.89（见「融合 CLIP 向量」与「指标」）。

## 数据和训练

数据不进仓库（`/data/` 已在 `.gitignore` 里），仓库里只有训练出来的头。要复现，按顺序跑四个工具：

```bat
REM 1) 四个「桶」的基础图：插画 / 照片 / 截图 + 一批欧美梗图
python tools\fetch_illustration_dataset.py --out data\datasets\kind --illustrations 1000 --photos 600 --memes 450 --screenshots 120
python tools\fetch_illustration_dataset.py --out data\datasets\kind --top-up --pages 3 --illustrations 600 --photos 0 --memes 0 --screenshots 0

REM 2) 动漫梗图 vs 带字插画（这是 v2 的关键数据）
python tools\fetch_meme_dataset.py --out data\datasets\meme_vs_illustration --positives 3000 --negatives 2000 --hard-negatives 1000

REM 3) 外部池子：中文表情包 / COCO 照片 / RICO 手机截图 / 维基照片（HF 分片并发下载）
python tools\fetch_extra_pools.py --which all --workers 16

REM 4) 拼成训练目录（按类名分子目录，跨类去重，带 train/val 划分）
python tools\build_kind_dataset.py --kind data\datasets\kind --meme data\datasets\meme_vs_illustration ^
  --extra data\datasets\extra --out data\datasets\kind8 --manifest data\datasets\kind8\manifest.jsonl
```

| 训练类 | 来自 |
| --- | --- |
| `插画/` | `kind/illustration-*.jpg` + `meme_vs_illustration/_插画/` 里**不带**字的那批 |
| `梗图/` | `meme_vs_illustration/梗图/*.jpg` + `kind/meme-*.jpg` + `_插画/` 里 `texted-*` 的带字图 + `extra/chinesebqb`（中文表情包）+ `extra/met-meme` |
| `照片/` | `kind/photo-*.jpg`（picsum + Wikimedia Commons 难例）+ `extra/coco-hf`（COCO 800）+ `extra/landscape` + `extra/picsum` |
| `截图/` | `kind/screenshot-*.jpg` + `extra/rico`（手机界面）+ `extra/desktop`（浏览器截图） |

跨类去重按 8×8 灰度均值哈希（几个下载器用不同 tag 查 safebooru，同一张图会重名，`--no-dedupe` 可关）。
本次实跑（kind8）：**插画 2,354 / 梗图 5,598 / 照片 2,270 / 截图 597 = 10,819 张，去重跳过 712 张**，
按 `index % 5 == 0` 确定性切出 2,170 张验证集（清单里带 `split`，训练器直接读，不再随机切）。

类不平衡是真实的：梗图占一半以上。所以训练一定带 `--class-weight`，否则截图和插画会被压着打。

### 训练

先要特征模型（`models/vit/model_features.onnx`，多一个 `features` 输出）：

```bat
python tools\add_feature_output.py

python tools\train_feature_plugin.py --data data\datasets\kind8 --loss ce --class-weight ^
  --semantic --cache data\datasets\kind8\embeddings_semantic.npz --out plugins\kind ^
  --id kind --name 画面类型 --target tag --threshold 0.5 ^
  --epochs 400 --lr 0.05 --l2 3e-3 --binary-label 插画 --priority 10
```

几个参数值得解释：

- `--loss ce` —— 走 softmax 交叉熵而不是多标签 sigmoid。它要求每张图**恰好一个**标签，
  导出的 ONNX 尾巴是 `Softmax`，`plugin.json` 里写 `"exclusive": true`、`"activation": "softmax"`，
  加载时 `plugins.py` 只取冠军类。用 `bce` 训出来的是「四个独立的是/否」，四类会同时亮。
- `--semantic` —— 把 Chinese-CLIP 的 512 维也拼进来（见下一节），`input_dim` 变成 1,280。
- `--class-weight` —— 逆频率加权再归一化到均值 1。截图只有 597 张，不加权会被 5,598 张梗图压着打。
- `--cache` —— 特征 npz 缓存，指纹是「路径 + 标签 + 大小 + mtime + 头尾各 8 KB 的哈希 + 要不要 CLIP」。
  调参重跑时命中缓存，几秒进入训练；动了图片就自动重算，换 `--semantic` 也不会用错缓存。
- `--binary-label 插画` —— 额外打一行「插画 vs 其余」的 accuracy / precision / recall / f1 / AUC，
  这才是「只想整理插画」那拨用户真正关心的那个数。
- `--threshold 0.5` —— 冠军低于它就不发标签（弃权）。

清单里有 `split` 时训练器**只按清单切**（会打印 `split from the manifest: 8649 train / 2170 val`），
不再随机分——否则同一张图可能这版在训练、下一版在验证，指标就没法横向比。

整轮在 RTX 5060 上约 55 分钟，几乎全花在抽特征上：10,819 张 ×（99 ms WD14 + 88 ms CLIP）。
确认用得上缓存就不是 55 分钟，是几十秒。
⚠️ **抽特征前先关掉所有在跑的 `albumcat serve`**：每个进程各持一个 DirectML 会话，抢起来会慢十倍
（实测 1.14 s/张 vs 83 ms/张）。

## 融合 CLIP 向量

WD14 那 768 维回答的是「这张图能打上哪些 danbooru 标签」——对**画了谁、画了什么**很敏感，
对**这张图长什么样**（有没有字、像不像聊天软件里转发的小图）并不直接。Chinese-CLIP 的 512 维
正好补这一块：它按「整张图说的是什么」编码，对「插画 + 描边字」这类组合比 WD14 清楚。

所以头吃的是 `[WD14 768 ‖ CLIP 512] = 1,280` 维，两个塔在服务端本来就是现成的：

- `plugins/kind/plugin.json` 里多一行 `"semantic_dim": 512`，插件层据此决定往后接 CLIP。
  宽度对不上会抛 `PluginError`，不会拿错的向量硬算；CLIP 拿不到时这个插件**弃权**，不猜。
- `albumcat serve` 里 CLIP 塔本来就为语义搜索加载着，**插件复用同一个实例**，不多占内存。
  手机端不用改：`/plan` 回来的还是同格式标签。
- 代价是每张图多约 90 ms（99 → 187 ms）。
- 实测：验证集 2,170 张全对 87.6%（纯 WD14 的上一版 87.1%，但结构不同——上一版 `插画` 只有
  79.7%，融合后 89.0%）；你自己那 135 张 held-out **83.0% → 85.9%**。

去 `--semantic` 并把 `"semantic_dim"` 删掉，就是这个头退化成上一版（`input_dim` 要跟着改回 768）。

## 指标

验证集 2,170 张（按清单的 `split` 切，不是随机）：

```text
exact-match (every label right): 87.6%      (训练集 91.9%)
label        n+   TP   FP   FN  precision  recall   auc
截图        115  110    1    5      0.991   0.957  1.000
插画        472  420  199   52      0.679   0.890  0.949
梗图      1,122  915   59  207      0.939   0.816  0.957
照片        461  455    8    6      0.983   0.987  1.000

truth \ guess    截图   插画   梗图   照片    -            (弃权)
截图              110    0    4    1    0   95.7% of 115
插画                0  420   49    2    1   89.0% of 472
梗图                1  199  915    5    2   81.6% of 1122
照片                0    0    6  455    0   98.7% of 461
```

再叠上分辨率先验，同一批 **88.6%**（只有 0.1% 的图弃权，所以「几乎每张都有答案」仍然成立）。

`插画` 的 precision 只有 0.679 是因为**梗图常常长得像插画**（梗图本身就是插画加字），
反过来 `梗图` 的 recall 0.816 说明还有 18% 的梗图被叫成插画。这两个数就是当前的天花板。

### 阈值换什么

同一批验证集上扫（`threshold` 就是 `plugin.json` 里那个，冠军低于它就不发标签）：

| `threshold` | 发标签比例 | 发出去的里面有多少对 | 说明 |
| --- | --- | --- | --- |
| 0.50 | 99.9% | 88.6% | 默认：几乎每张都给答案 |
| 0.55 | 98.3% | 89.1% | |
| 0.60 | 96.9% | 89.6% | 放弃 3% 拿不准的图 |
| 0.70 | 93.4% | 90.7% | 放弃 7% |

只想整理插画、宁愿少几张也要干净，就把 `threshold` 改成 `0.6`；想要「每张都有个类型」，
就保持 `0.5`。融合 CLIP 之后 softmax 更自信了，阈值能换到的收益比 v2 小（v2 时 0.5→0.6 涨 2 个点，
现在只有 1 个点）——真正的分界在「梗图 vs 插画」这个语义本身，不在置信度上。
**别靠调阈值救梗图**：被误判的梗图在 `插画` 上往往是 0.9+。

### 域外表现

喂训练集里完全没有的东西（`.tmp/hard/`，不进仓库；`.tmp/eval_ood.py` 一次量完）：

| 挑战 | 结果 |
| --- | --- |
| 真人 cosplay 照片 12 张 | 11 `照片` / 1 `梗图` |
| 手办照片 10 张 | 7 `照片` / 2 `梗图` / 1 弃权 |
| 手办白底图 8 张 | 4 `梗图` / 4 `插画` |
| cosplay 图 8 张 | 7 `插画` / 1 `梗图` |
| 艺术照片 13 张 | 9 `梗图` / 3 `插画` / 1 `照片` |
| 动画截图 8 张 | 5 `梗图` / 3 `插画` |
| AI 生成图 8 张 | 5 `梗图` / 3 `插画` |

读法：

- **照片这一侧是可靠的**：真人 cosplay、手办照片基本都进 `照片`，这正是「不要把真实照片塞进插画」
  那条底线。
- **白底商品图 / 动画截图 / AI 画仍然偏 `梗图`**：它们本来就是「合成出来的平面图」，和梗图在特征上
  贴得近。这类图会从 `插画` 筛选里消失（是**漏**，不是把梗图混进插画）。
- 想稳妥就按「照片 / 截图 / 梗图」**反向**筛，或者把阈值提到 0.6 少要答案。
- 训练同源但没训过的 safebooru 梗图（验证集 577 张）84.2% 全对、带字插画（528 张）77.1% 全对——
  这两类天生互相借位，`梗图`/`插画` 的错判基本都出在它们之间。
- 拿自己的相册量：`--truth-dir` 打开网页看板，比这张表更有说服力。

### 分辨率先验（`size_prior`）

到分类头手里的图，一律是 448×448 的正方形——原图是 320 像素的表情包还是 6,000 像素的壁纸，
模型根本不知道。而分辨率本身是个**很干净**的线索：几百像素的图基本是聊天软件里存下来的东西，
四五千像素的不可能是梗图。所以把它作为「先验」加在分类头**之后**，而不是塞进特征：

```json
"size_prior": {"label": "梗图", "small_edge": 640, "large_edge": 2400, "boost": 0.8, "suppress": -0.4}
```

- 只动 `梗图` 这一个标签的 logit：长边 ≤ `small_edge` 加 `boost`，≥ `large_edge` 加 `suppress`
  （这里是减），中间按 **log2 长边**线性插值，两端截断。改完重新归一化，标签顺序不变，
  胜负照旧由 softmax + 阈值决定——**不新增、不删除任何标签**，最坏情况只是把冠军换掉。
- **只在客户端说了原图尺寸时生效。** 手机上传的是 448 缩略图，服务端绝不从上传的字节里猜尺寸；
  `/plan`、`/classify` 都要求 `width`/`height`，没给就当作「不知道」，先验等于关掉。
  （v0.5.x 的 APK 已经会发这两个字段；更早的 APK 不发，先验静默失效，其余行为不变。）
- 数字写在 `plugin.json` 里，`albumcat plugins` 会把它打出来：

  ```
  kind                     feature  tag           10  0.50  True
                           size prior: 梗图 +0.80 at <= 640 px, -0.40 at >= 2400 px
  ```

  网页看板 `/ui` 每张卡片也会写「尺寸 1080×2400 · 尺寸先验 梗图 -0.32（梗图 61% → 48%）」，
  并显示原始分数，方便判断该不该调。

**量出来的效果**（`.tmp/eval_size_prior.py`，每类 60 张、按类真实尺寸重绘：梗图 320–800、
插画 1024–2048、照片 2400–4608、截图 1080–2400；仓库里的样本都是 640 px，只能这样造尺寸）：

| 设置 | 全对 |
| --- | --- |
| 关 | 95.0%（228/240） |
| 现在这一版 640/2400 +0.8/−0.4 | 95.0%（228/240） |
| 网格里最好的一档（480/1600 +0.4/−0.4） | 95.4%（229/240） |

到了 v5 这版头，在这个造的尺寸集上已经**先验不加也不掉**——它自己就把尺寸信号从 CLIP 特征里
学到了一些。但先验在真实数据上还有净收益，所以留着：

- kind8 验证集：关 87.7% → 开 **88.6%**（73 张被翻动：47 张改对、26 张改错）。
- 你自己那 135 张：85.2% → **85.9%**。

**没有换 480/1600 那档**：它恰好压在我构造的插画尺寸边界上（插画一律 ≥1024），属于对假数据过拟合；
真实相册里 1080×1920 的整屏梗图很常见，`large_edge` 定在 1600 会把它们按「大图」压下去。
想试可以自己改 `plugin.json`，`/ui` 会实时显示每张的先验 delta。

## 试过但没用的方向

都不是拍脑袋，是同一批数据上量出来的（域内是 kind8 验证集，域外是你那 135 张）：

| 做法 | 结果 |
| --- | --- |
| 只用 768 维 WD14 特征（v4） | 验证 87.1%（`插画` 79.7%）、你的 135 张 83.0% |
| **768 + CLIP 512 = 1,280 维（v5，现在这一版）** | 验证 87.6%（`插画` 89.0%）、你的 135 张 **85.9%** |
| 只用标签分数 | AUC 0.821 —— 标签是硬阈值，丢掉了 softmax 里那些「差一点」的信息 |
| 768 维 + 41 个版面/文字标签的分数（809 维） | AUC 0.853、acc 78.6% —— 没有增益，标签本来就是同一个 ViT 推出来的 |
| 只用 Chinese-CLIP 512 维 | AUC 0.828 —— 单靠自己不如 WD14，拼起来才赢 |
| 模糊增强（训练时把训练图缩小 + 高斯模糊 + 降 JPEG 质量再存一份副本） | clean −0.4、mild −0.1、强模糊 −2.0，全都更差；两个头按 logit 平均也只把强模糊从 70.1% 抬到 72.4%，clean 反而掉 0.3 |
| 另训一个「梗图 vs 插画」二分类头 | 验证 81.9%，但**照片 30% 误判梗图**（域外漂移），已删除 |

两行值得记：

- 单输出 sigmoid 头在域内看着和四分类差不多，到了域外会把真实照片叫成梗图（平均分 0.84），
  比四分类更容易害人——所以仓库里只留四分类头。
- 模糊增强花了一个下午，结论是「模糊是真问题（同一批 val，强模糊下全场从 86.6% 掉到 70%），
  但训练时加模糊副本治不了」：加得越多，梗图那一侧越差，因为它把「带字小图」这一类的边界揉糊了。
  所以产品里不做模糊增强，模糊的图就让它弃权或判错。

## 自己看一眼：网页看板

指标是纸上的，你相册里的图才是真的。电脑端起着服务时，打开：

```
http://127.0.0.1:8899/ui
```

**选一个文件夹**（或者把文件夹整个拖进页面），里面的图会先平铺出来，缩略图只在你的浏览器里生成，
这之前一张都没上传。点「开始分类」之后才会一张张送过去，进度条走完就自动切成四堆：

```
插画 18 张 · 38%     梗图 12 张 · 25%     照片 9 张 · 19%     截图 9 张 · 19%
```

按分类分开显示，就是拿来跟相册对照的：`梗图` 那堆里混进来的插画一眼就能看见。
没过阈值的单独归到「未识别」——这正是手机上看不到的信息：手机只收到冠军的那一个词，
`梗图 0.48 对 插画 0.51` 和 `梗图 0.02` 在手机上都只是一个标签（或都没有）。

点开任意一张是详情：四条横条（`截图 / 插画 / 梗图 / 照片` 的完整概率）、阈值、耗时、
原图尺寸和尺寸先验挪了多少分、认出的角色与标签。想只盯着边界那几张，就用「未识别」筛选；
「全部平铺」可以切回上传顺序。分类途中可以「停止」，再按一次只补没分的那些。

给脚本用的话是同一个后端：

```bat
curl -X POST http://127.0.0.1:8899/classify ^
  -H "Content-Type: application/json" ^
  -d "{\"images\": [{\"id\": \"a\", \"name\": \"a.jpg\", \"image\": \"<base64>\"}]}"
```

返回里 `classifiers[0]` 是 `{id, name, exclusive, threshold, labels, scores, picked}`，
`scores` 与 `labels` 一一对应、**没有被阈值过滤**；`picked` 是实际会发出的那个标签（弃权时是 `null`）。
多张一起发最多 24 张，坏掉的那张只会自己带 `"ok": false`，不影响其余。

页面是 `src/albumcat/webui.py` 里的一个字符串，没有构建步骤、不连 CDN、不落盘：
图片在浏览器里缩到长边 1024 才发出去，原图尺寸单独随请求带上（分类器只看得到 448 的方图），
服务端用同一套管线算完就丢，不写缓存、不碰相册数据库。服务端设了 `--token` 时，页面右上角填同一个令牌。

### 让它自己算准确度

「看着差不多」不算结论，所以页面也能自己打分。把测试图按类别放好，启动时指一下这个目录：

```bat
tools\albumcat.cmd serve --truth-dir E:\AlbumCategories\meme_chahua_samples
```

```
meme_chahua_samples\
  chahua\        32 张        <- 文件夹名就是答案
  meme\          63 张
  photo\         30 张
  screenshoot\   10 张
  all\          135 张        <- 拍平的一份，上传这个
```

页面把 `all` 里的图全部选中、分类完，顶上的面板就给出整轮准确度和每个类别的命中：

```
77.8%   判对 105 / 135 张
插画 32 张  ■■■■■■■■░░  27 张判对 · 84%  误判 梗图 5
梗图 63 张  ■■■■■■■■░░  54 张判对 · 86%  误判 插画 6、未识别 2、截图 1
照片 30 张  ■■■■□□□□□□  16 张判对 · 53%  误判 插画 10、未识别 2、截图 2
截图 10 张  ■■■■■■■■░░   8 张判对 · 80%  误判 插画 1、梗图 1
```

判错的图右上角有个红叉，左上角写着判成了什么；点「只看判错的」就只剩那几张，
点开单张还能看到「标准答案 X · 判成 Y 62%」。规则很朴素：**文件名在哪个类别文件夹里出现过，
它的答案就是那个类别**——所以 `all\` 里是拍平的副本也照样算得出来。
`chahua` / `插画`、`meme` / `梗图` 这些写法都认，中文英文都行，前缀后缀（`1_chahua-2026`）也能认。

不设 `--truth-dir` 就完全不出现这块面板，页面和以前一模一样。
标准答案是本地目录扫出来的，只回文件名和类别，不读图片内容。

## 接入

```bat
tools\albumcat.cmd plugins
REM kind  feature  tag  10  0.50  True
tools\albumcat.cmd plan 你的图.jpg
```

`plugins/kind/` 里有三个文件：

| 文件 | 说明 |
| --- | --- |
| `head.onnx` | 20,684 B。`Gemm(transB=1)` → `Softmax`，输入 1,280 维（768 WD14 + 512 CLIP） |
| `labels.json` | 四个类名，顺序 = softmax 列顺序 |
| `plugin.json` | `kind: feature`、`target: tag`、`priority: 10`、`threshold: 0.5`、`input_dim: 1280`、`semantic_dim: 512`、`exclusive: true`、`activation: softmax`、模型 `sha256` |

`tests/test_shipped_plugins.py` 会核对 id/目录名、`labels.json` 与 manifest 一致、`sha256` 一致、
ONNX 的输入宽度 = `input_dim`（= 768 + `semantic_dim`）、输出宽度 = 标签数、softmax 每行和为 1——改了头忘了改 manifest 会直接红。

这是普通 `feature` 插件，`plugins/` 下任何目录都会被自动加载；不需要改配置、不需要重发版。
`target: tag` 的标签是**扁平叶子**（`插画` 一层，没有 `类型|` 前缀）；想让它落到树里，
用自定义规则把 `then.path` 写成 `["类型", "{display}"]`（见 [插件](PLUGINS.md)）。

插件发出的普通标签**不占** `max_general_tags_per_image` 的名额，也仍然受 denylist 约束：
25 个 WD14 标签不会把你自己的分类结果挤掉（`src/albumcat/rules.py` 第 4 段）。

### 已经在手机上打过旧标签怎么办

手机端保存标签用的是整行替换（`appTags.setTagsById`），所以：

1. 把新头放进 `plugins/kind/`（仓库里已经是新的），重启 serve；
2. 手机端进 `AI 打标签`，**取消**「跳过已经有标签的图片」，重跑一遍；
3. 每张图打完的标签会**整行覆盖**，v1 留下的 `插画` 不会残留。

只补跑一部分也行：跳过勾着，没标签的才跑，有旧标签的保持原样。

## 边界与后续

- 四类互斥是**刻意**的：表情包常常是截图，梗图常常是插画加字，硬要四类各判一次只会互相矛盾。
- 只在 640 px 缩略图上判据足够；`/plan` 收到什么就以什么为准（手机端上传 640–1024 px）。
- 想加第五类（比如「漫画分镜」和「动画截图」分开），建子目录重训即可；
  `labels.json` 和 `head.onnx` 会一起更新。
- 已经走过的一条路是 **WD14 + CLIP 拼特征**（这一步已经做了，见「融合 CLIP 向量」）。
  再往上，最有希望的是**用 OCR 的文字框面积/行数当正交特征**——「这张图有多少字」比「像不像插画」
  更接近梗图的定义，而现在只有「有字/没字」这一个布尔量。
